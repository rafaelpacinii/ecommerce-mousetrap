# MouseTrap — Authoritative Business Rules Specification (`BR-*`)

This document is the **single authoritative catalog of business rules** for the MouseTrap gaming-mouse e-commerce platform (`v1.0.0` → `v2.0.0`, Flyway `V1`–`V15`). It governs `api/`, `web/`, `infra/`, and the domain/relational models in [docs/modelagem/README.md](modelagem/README.md).

> **MANDATORY AI GOVERNANCE LOCK:** Every AI coding agent (Codex, Antigravity, Claude Code, Copilot, or custom subagent) **MUST** consult the applicable sections of this file before designing or modifying any database migration, JPA entity, repository, service, DTO, REST contract, or Angular workflow. **No agent may override, relax, delete, bypass, or invent any `BR-*` business rule without explicit prior authorization from the user.**

## 1. Store Scope, Identity, Roles & Account Ownership (`BR-IAM`)

| ID | Status | Rule & Enforcement |
| :--- | :---: | :--- |
| **`BR-IAM-01`** | **Implemented (`V1`–`V9`)** | **Single-Store Architecture (No Multitenancy):** MouseTrap operates a single gaming-mouse store with one unified inventory. Never introduce `tenant_id`, multi-seller isolation, organization switchers, or client-supplied store/tenant headers. |
| **`BR-IAM-02`** | **Implemented (`V4`)** | **Externalized OIDC PKCE Authentication:** User credentials, registration, email verification, and password recovery live exclusively in Keycloak (`mousetrap` realm, public SPA client `mousetrap-web` using Authorization Code + PKCE `S256`, resource server audience `mousetrap-api`, exact redirect URIs and CORS origins without wildcards). PostgreSQL never stores user passwords or credential hashes. |
| **`BR-IAM-03`** | **Implemented (`V4`)** | **Closed Role Model (`customer` & `admin`):** Only two realm roles govern application access: `customer` and `admin`. Self-service registration always assigns `customer` only; privileges can never be elevated through application endpoints or forms. Users holding `admin` may also browse and purchase as customers under their own JWT `sub`. |
| **`BR-IAM-04`** | **Implemented (`V4`)** | **Authoritative Backend Authorization:** Angular route guards (`authGuard`, `adminGuard`) and hidden UI buttons exist solely for UX navigation. Every non-public Quarkus endpoint/service must enforce `@Authenticated` or `@RolesAllowed`, returning `401 Unauthorized` when unauthenticated and `403 Forbidden` when role or permission checks fail. |
| **`BR-IAM-05`** | **Implemented (`V4`–`V7`)** | **Strict JWT Subject Ownership:** Customer profiles (`/clientes/me`), phones, addresses (`/clientes/me/enderecos`), wishlists (`/desejos`), and shopper orders (`/pedidos`, `/pedidos/me`) are owned strictly by the verified JWT `sub` claim (`Cliente.identidadeSubject`, 1–255 chars). Never trust a `clienteId` sent by the browser to access or mutate data; cross-customer access attempts must be rejected (`404` or `403`) without leaking foreign records. |
| **`BR-IAM-06`** | **Implemented (`V4`)** | **Verified Email Prerequisite:** Creating or updating a self-service profile (`PUT /clientes/me`) requires a valid JWT with `email_verified == true` and a non-blank, normalized lowercase email (`<= 254` chars). |
| **`BR-IAM-07`** | **Implemented (`V4`)** | **No Automatic Account Claiming by Email:** If an authenticated user's email matches a pre-existing `Cliente` row whose `identidade_subject` is `NULL` (or belongs to another subject), `/clientes/me` must reject the write with `409 Conflict` rather than silently linking accounts. Account linkage requires explicit administrative action (`PUT /clientes/{id}/identidade`, `@RolesAllowed("admin")`) under `PESSIMISTIC_WRITE` lock, verifying normalized email equality and confirming neither the `Cliente` nor the target `subject` is already linked. |
| **`BR-IAM-08`** | **Implemented (`V4`)** | **Protected Email on Linked Profiles:** Once a `Cliente` record is linked to a non-null `identidadeSubject`, administrative CRUD (`PUT /clientes/{id}`) cannot overwrite `email` to a different address (`409 Conflict`). |
| **`BR-IAM-09`** | **Implemented (`V4`)** | **In-Memory Bearer Tokens & Keycloak `HttpOnly` SSO Cookies (Zero `localStorage`):** Access and refresh tokens must remain strictly in `keycloak-js` runtime memory and are never persisted in `localStorage` or `sessionStorage` (`sessionStorage` may hold only the sanitized relative `mousetrap.returnUrl`). Persistent SSO across page reloads uses Keycloak's `HttpOnly` session cookies via `check-sso` (`silent-check-sso.html`), while `authInterceptor` forwards `Authorization: Bearer` exclusively to the configured API origin (`settings.apiUrl`). |

## 2. Catalog, 3NF Hardware Components, Categories & Media (`BR-CAT`)

| ID | Status | Rule & Enforcement |
| :--- | :---: | :--- |
| **`BR-CAT-01`** | **Implemented (`V1`)** | **Commercial Unit per SKU (Color Variants):** Each `Mouse` row is an independent sellable SKU (`sku = upper(trim(sku))`, `^[A-Z0-9][A-Z0-9._-]*$`, 1–50 chars, globally `UNIQUE`). Distinct colorways of the same mouse model are separate `Mouse` records with independent SKU, price, gallery, and stock. |
| **`BR-CAT-02`** | **Implemented (`V1`, `V9`) + Planned (`V10`)** | **Case-Insensitive Catalog Uniqueness:** `Marca.nome` (2–100 chars), `Sensor.modelo` (2–100 chars), `SwitchMouse.modelo` (2–100 chars), `Pais.nome` (2–100 chars), `Pais.siglaIso` (`^[A-Z]{2}$`), and planned `Categoria.nome` / `Categoria.slug` (`V10`) are trimmed and enforced as unique case-insensitively (`UNIQUE` + `lower(...)` index). |
| **`BR-CAT-03`** | **Implemented (`V3`) + Planned (`V10`)** | **Public Storefront Visibility Gate:** Public catalog endpoints (`/catalogo/mouses`, `/catalogo/mouses/{id}`, `/catalogo/filtros`) expose **only** products where `mouse.ativo == true` AND `mouse.marca.ativo == true` (and, starting in `V10`, `mouse.categoria == null || mouse.categoria.ativo == true`). Requesting an inactive mouse or a mouse of an inactive brand via `/catalogo/mouses/{id}` returns `404 Not Found`. |
| **`BR-CAT-04`** | **Implemented (`V3`)** | **Out-of-Stock Storefront Retention:** Active products with `quantidadeEstoque == 0` remain visible in public catalog listings and detail pages labeled unavailable (`Esgotado` / `Indisponível`) unless the caller filters with `emEstoque=true`. They cannot be checked out while stock is zero. |
| **`BR-CAT-05`** | **Implemented (`V1`, `V3`)** | **Connection & Grip Multiplicities:** Every `Mouse` must have between `1` and `3` distinct `TipoConexao` values (`1=USB`, `2=BLUETOOTH`, `3=RECEPTOR_USB`) and between `0` and `3` distinct `Pegada` values (`1=PALM`, `2=CLAW`, `3=FINGERTIP`). |
| **`BR-CAT-06`** | **Implemented (`V1`, `V3`, `V9`)** | **Physical & Technical Specification Bounds:** `Mouse` requires `nome` (2–150 chars), `descricao` (1–5000 chars), `cor` (1–50 chars), `dpiMaximo > 0`, `quantidadeBotoes > 0`, and `pesoGramas > 0` (`numeric(8,2)`). Optional fields must satisfy `comprimentoMm > 0`, `larguraMm > 0`, `alturaMm > 0` (`numeric(5,1)`), `autonomiaBateriaHoras > 0`, and `pollingRate` strictly within `{125, 250, 500, 1000, 2000, 4000, 8000}` Hz. `Marca.anoFundacao`, when present, must be between `1900` and `2100`. |
| **`BR-CAT-07`** | **Implemented (`V9`)** | **3NF Optical Sensor & Micro-Switch Integrity:** Sensor attributes (`fabricante`, `dpiMaximo > 0`, `ips > 0`, `aceleracaoG > 0`) live on `Sensor`; switch attributes (`fabricante`, `tipoSwitch` `1=OPTICO / 2=MECANICO`, `durabilidadeMilhoesCliques > 0`, optional `forcaAtuacaoGf > 0`) live on `SwitchMouse`. Service writes synchronize normalized `sensorEntidade` and `switchEntidade` references alongside transitional compatibility fields. |
| **`BR-CAT-08`** | **Implemented (`V9`)** | **Warranty Bounds & Brand Default Inheritance:** Both `Marca.garantiaPadraoMeses` and `Mouse.garantiaMeses` must stay within `1..120` months. Creating a `Mouse` without an explicit `garantiaMeses` inherits `marca.garantiaPadraoMeses` (default `12`). |
| **`BR-CAT-09`** | **Implemented (`V1`, `V9`)** | **Optimistic Locking on Catalog Mutations:** `Mouse`, `Marca`, `Sensor`, `SwitchMouse`, and planned `Categoria` maintain `@Version` (`versao >= 0`). `PUT /mouses/{id}` requires the client's current `versao` and rejects stale concurrent writes with `409 Conflict`. |
| **`BR-CAT-10`** | **Implemented (`V3`)** | **Ordered Product Image Gallery:** A `Mouse` supports `0..12` `ImagemMouse` items, each requiring an `http`/`https` URL (`<= 2048` chars), non-blank `textoAlternativo` (`1..200` chars), and unique nonnegative `ordem` (`UNIQUE(mouse_id, ordem)`). The lowest `ordem` serves as the cover image. On `PUT /mouses/{id}`, `imagens == null` preserves the existing gallery for backward compatibility, whereas an explicit list replaces it (`[]` removes all images). |
| **`BR-CAT-11`** | **Implemented (`V8`)** | **Cloudflare R2 Upload Validation & Security:** `POST /imagens/{destino}` requires `@RolesAllowed("admin")` and `destino` in `{"mouses", "marcas"}`. Uploaded files must be non-empty, `<= 5 MiB` (`5,242,880` bytes; multipart ceiling `6 MiB`), and match binary magic bytes for `image/png`, `image/jpeg`, or `image/webp` (SVG, HTML, and mismatched MIME types are rejected with `400`). Objects use generated keys `<destino>/<uuid>.<ext>` and `Cache-Control: public, max-age=31536000, immutable`. R2 credentials never leave the backend, and raw AWS SDK exceptions are never logged. |
| **`BR-CAT-12`** | **Implemented (`V1`, `V6`) + Planned (`V10`)** | **Catalog Deletion Protection vs. Deactivation:** A `Marca` with any linked `Mouse` cannot be deleted; a `Categoria` (`V10`) with any linked `Mouse` cannot be deleted (`ON DELETE RESTRICT`); a `Mouse` referenced by any `ItemPedido` cannot be hard-deleted. Historical catalog items must be deactivated (`ativo = false`) rather than erased. Deleting an unreferenced `Mouse` cascades only to `mouse_conexao`, `mouse_pegada`, `imagem_mouse`, and `desejo`. |
| **`BR-CAT-13`** | **Planned (`V15` — Epic E7)** | **Safe R2 Orphan Cleanup:** Database transactions never synchronously delete R2 objects (avoiding broken images on transaction rollback). The `E7` orphan-cleanup routine may delete an R2 object only after confirming zero references in `imagem_mouse.url` and `marca.logomarca_url` and observing a safety grace age for unsaved admin form uploads. |
| **`BR-CAT-14`** | **Planned (`V10` — Epic E2)** | **Single-Level Product Categories (`Categoria`):** Storefront taxonomy uses a flat, normalized `Categoria` entity (`nome`, URL-safe `slug`, `descricao`, `ativo`, `versao`) without arbitrary-depth category trees unless explicitly authorized later. |
| **`BR-CAT-15`** | **Planned (`V11` — Epic E3)** | **Curated Weekly Highlights:** `GET /catalogo/mouses/destaques` returns only active mice of active brands (and active categories) with `destaque = true`, sorted deterministically by `ordem_destaque ASC NULLS LAST, id DESC`. |
| **`BR-CAT-16`** | **Planned (`V11` — Epic E3)** | **Authentic Best-Sellers Ranking (`mais-vendidos`):** Sorting by `ordenar=mais-vendidos` ranks active catalog products strictly by real sold unit volume (`SUM(item_pedido.quantidade)`) across orders in `PAGO`, `ENVIADO`, or `ENTREGUE`, breaking ties deterministically; artificial sales counters are prohibited. |

## 3. Customer Profiles, Phones, Addresses & ViaCEP (`BR-CLI`)

| ID | Status | Rule & Enforcement |
| :--- | :---: | :--- |
| **`BR-CLI-01`** | **Implemented (`V2`, `V9`)** | **Customer Identity & Email Normalization:** `Cliente.nome` requires 2–100 trimmed characters. `Cliente.email` (`<= 254` chars) is trimmed, lowercased (`email = lower(trim(email))`), format-validated, and globally `UNIQUE`. |
| **`BR-CLI-02`** | **Implemented (`V9`)** | **CPF & Birth Date Rules:** `Cliente.cpf` is optional; when provided, punctuation is stripped, it must match `^[0-9]{11}$`, and it is globally `UNIQUE`. `Cliente.dataNascimento`, when provided, cannot be a future date. |
| **`BR-CLI-03`** | **Implemented (`V9`)** | **Normalized Customer Phones (`TelefoneCliente` `1:N`):** Customers may store `0..5` phone numbers (`ddd` `^[0-9]{2}$`, `numero` `^[0-9]{8,9}$`, `tipoTelefone` `1=CELULAR / 2=RESIDENCIAL / 3=COMERCIAL`, `principal`). Duplicate `(cliente_id, ddd, numero)` entries are forbidden, and at most one phone per customer is marked `principal = true` (if phones exist and none is marked, the first is promoted automatically). |
| **`BR-CLI-04`** | **Implemented (`V2`, `V5`)** | **Authoritative Server-Side ViaCEP Resolution:** Every CEP lookup (`/ceps/{cep}`) and every address write normalizes CEP to 8 digits (`^[0-9]{8}$`) and validates it on the backend through ViaCEP. Client-sent city/UF/IBGE values are never trusted: the server resolves `Estado` (27 seeded Brazilian UFs) and upserts `Municipio` by unique 7-digit `codigoIbge`. Malformed or non-existent CEPs return `400 Bad Request`; ViaCEP timeouts or invalid upstream responses return `503 Service Unavailable`. |
| **`BR-CLI-05`** | **Implemented (`V5`)** | **Owned Address Book & Single Principal Address:** Each `Endereco` belongs to one `Cliente` (`apelido` 1–60 chars, `destinatario` 2–150 chars, `logradouro` 1–200 chars, `bairro` 1–100 chars, `numero` 1–20 chars supporting `"S/N"`, optional `complemento <= 100` chars). Partial unique index `uk_endereco_cliente_principal` enforces at most one `principal = true` address per customer; adding the first address or setting `principal = true` demotes the previous default, and deleting the default promotes a remaining address. |
| **`BR-CLI-06`** | **Implemented (`V5`)** | **Last-Address Deletion Guard:** A customer cannot delete their only remaining `Endereco`; at least one saved address must remain once an address book exists (customers may edit that address in place). |
| **`BR-CLI-07`** | **Implemented (`V5`, `V6`)** | **Decoupling of Saved Addresses from Historical Orders:** Editing or deleting a saved `Endereco` never modifies past or pending `Pedido` records because orders embed an immutable `EnderecoEntrega` copy (`entrega_*`). |
| **`BR-CLI-08`** | **Implemented (`V6`, `V9`)** | **Customer Historical Deletion Protection:** A `Cliente` who owns one or more `Pedido` rows cannot be deleted (`ON DELETE RESTRICT`); deactivate via `Cliente.ativo = false` instead. |

## 4. Browser Cart & Persistent Wishlist (`BR-CRT`)

| ID | Status | Rule & Enforcement |
| :--- | :---: | :--- |
| **`BR-CRT-01`** | **Implemented (`v1.0.0`)** | **Browser-Only Cart Without Stock Reservation:** The cart is stored solely in Angular state and browser `localStorage` (`IDs` + `quantities`), does not synchronize across devices, creates no database rows, freezes no prices, and reserves zero stock. |
| **`BR-CRT-02`** | **Implemented (`v1.0.0`)** | **Cart Quantity & Line Limits:** Cart quantities must be integers `>= 1`, capped by known available stock in the UI and validated on the server (`1..999` units per SKU, `1..100` distinct SKUs per checkout). |
| **`BR-CRT-03`** | **Implemented (`v1.0.0`)** | **Confirmed-Order Selective Cart Deduction:** The SPA removes purchased quantities from the local cart **only** after the API confirms order creation (`201 Created`), tracking bounded `chaveCheckout` receipts so network retries or page reloads never deduct items twice or wipe unpurchased cart items. |
| **`BR-CRT-04`** | **Implemented (`V7`, `V9`)** | **Persistent Subject-Scoped Wishlist (`Desejo`):** Wishlist items are persisted per `identidadeSubject` (`UNIQUE(identidade_subject, mouse_id)`) and linked to `Cliente` (`cliente_id`) when a profile exists. Wishlists store no quantities, freeze no prices, and reserve no stock. |
| **`BR-CRT-05`** | **Implemented (`V7`)** | **Wishlist Capacity & Concurrency Serialization:** Each subject may store at most `500` wishlist items, enforced under a PostgreSQL transaction advisory lock (`pg_advisory_xact_lock`). Adding an already saved product is idempotent; removing a missing product is a safe no-op. |
| **`BR-CRT-06`** | **Implemented (`V7`)** | **Wishlist Addition Gate & Post-Purchase Retention:** Only products with `mouse.ativo == true` and `marca.ativo == true` can be newly added to a wishlist (`404` otherwise). Products that later become out of stock or inactive remain visible and removable in the user's wishlist, and buying a wishlisted mouse does **not** auto-remove it. |

## 5. Money Arithmetic, Freight & Discount Coupons (`BR-PRC`)

| ID | Status | Rule & Enforcement |
| :--- | :---: | :--- |
| **`BR-PRC-01`** | **Implemented (`V1`, `V6`) + Planned (`V15`)** | **Exact Monetary Representation (Zero Float/Double):** All backend prices, subtotals, freight, discounts, and payment amounts use `BigDecimal` scaled to 2 decimal places (`RoundingMode.HALF_UP`) and PostgreSQL `NUMERIC`. `float` and `double` money math is forbidden. Existing REST DTOs preserve decimal BRL numbers for compatibility; new client calculations must use integer cents, with `precoCentavos` scheduled in `V15` (Epic E7). |
| **`BR-PRC-02`** | **Implemented (`V6`) + Planned (`V12`)** | **Server-Authoritative Totals:** `ItemPedido.subtotal = precoUnitario * quantidade`; `Pedido.subtotal = SUM(ItemPedido.subtotal)`; `Pedido.total = subtotal - valorDesconto + frete` (`valorDesconto = 0` prior to `V12`). Client-calculated prices, discounts, freight, or totals are never trusted as authoritative. |
| **`BR-PRC-03`** | **Implemented (`V6`)** | **Price & Freight Drift Detection (`409 Conflict`):** `POST /pedidos` compares each item's `precoEsperado` and the order's `freteEsperado` (from `POST /pedidos/revisao`) against current server values. Any discrepancy aborts checkout with `409 Conflict` so the customer explicitly re-reviews updated values. |
| **`BR-PRC-04`** | **Implemented (`V6`, `V9`) + Planned (`V15`)** | **Server-Computed Freight & Delivery Estimate:** Freight (`frete >= 0.00`) and delivery estimate (`prazoDiasUteis >= 1`) are calculated by the backend from the destination CEP (`frete.valor-padrao` default `29.90`, `frete.prazo-dias-uteis` default `5`), normalized with `Transportadora` (`V9`) and extensible via `FreteGateway` (`V15`). |
| **`BR-PRC-05`** | **Planned (`V12` — Epic E4)** | **Coupon Eligibility Rules (`Cupom`):** `Cupom.codigo` is normalized with `upper(trim(codigo))` (`UNIQUE`, 3–40 chars). A coupon is redeemable only if `ativo == true`, current `Instant` is within `[validoDe, validoAte]`, `pedido.subtotal >= valorMinimoPedido`, and `limiteUsos == null || quantidadeUsada < limiteUsos`. |
| **`BR-PRC-06`** | **Planned (`V12` — Epic E4)** | **Coupon Discount Math & Zero Floor:** `TipoDesconto.PERCENTUAL (1)` (`0 < valorDesconto <= 100`) computes `round(subtotal * valorDesconto / 100, 2, HALF_UP)`; `TipoDesconto.VALOR_FIXO (2)` (`valorDesconto > 0`) subtracts a fixed BRL amount. Applied `Pedido.valorDesconto` is capped at `Pedido.subtotal` so net merchandise value is never negative (`>= 0.00`), and freight is never turned negative. |
| **`BR-PRC-07`** | **Planned (`V12` — Epic E4)** | **Atomic Coupon Redemption, Snapshot & Reversal:** Redeeming a coupon locks `Cupom` with `PESSIMISTIC_WRITE`, increments `quantidadeUsada`, and snapshots `cupom_id`, `codigo_cupom`, and `valor_desconto` onto `Pedido`. If the order transitions to `CANCELADO`, `EXPIRADO`, or `REEMBOLSADO`, `quantidadeUsada` is decremented atomically at most once. |

## 6. Transactional Checkout, Concurrency, Stock & Order Lifecycle (`BR-ORD`)

| ID | Status | Rule & Enforcement |
| :--- | :---: | :--- |
| **`BR-ORD-01`** | **Implemented (`V6`)** | **Order Line Constraints:** Every `Pedido` must contain `1..100` distinct `ItemPedido` lines, with `quantidade` in `1..999` per line and no duplicate `mouse_id` within the same order (`UNIQUE(pedido_id, mouse_id)`). |
| **`BR-ORD-02`** | **Implemented (`V6`)** | **Checkout Idempotency & Payload Fingerprint (`chaveCheckout`):** `POST /pedidos` requires a UUID `chaveCheckout`, serialized via `pg_advisory_xact_lock` and paired with a SHA-256 `requisicaoHash` of the normalized request. Replaying the same key by the same subject with the identical payload returns the existing `Pedido`; reusing `chaveCheckout` with a different payload or by another user fails with `409 Conflict`. |
| **`BR-ORD-03`** | **Implemented (`V6`)** | **Deadlock-Free Deterministic Lock Ordering:** Checkout acquires locks in strict order: (1) advisory lock on `chaveCheckout`, (2) `PESSIMISTIC_READ` on `Cliente` and `Endereco` verifying subject ownership, (3) `PESSIMISTIC_WRITE` on all requested `Mouse` rows ordered by `mouse.id ASC`, and (4) `PESSIMISTIC_READ` + entity refresh on each `Marca` (plus `Categoria` in `V10` and `Cupom` write-lock in `V12`). This prevents deadlocks and concurrent overselling or brand deactivation races. |
| **`BR-ORD-04`** | **Implemented (`V6`)** | **Atomic Stock Deduction at Checkout:** `Mouse.quantidadeEstoque` is decremented immediately inside the checkout transaction when creating `Pedido` in `AGUARDANDO_PAGAMENTO`. If any requested SKU is inactive, belongs to an inactive brand, or lacks sufficient stock, the entire order rolls back. Stock is **never** deducted again when paying, shipping, or delivering. |
| **`BR-ORD-05`** | **Implemented (`V6`, `V7`)** | **Immutable Commercial & Delivery Snapshots:** `ItemPedido` copies `sku`, `nome`, `cor`, `marca`, and `precoUnitario` (`> 0`) at checkout; `Pedido` embeds `EnderecoEntrega` (`entrega_*`) and snapshots `transportadora` text upon shipment. Historical order lines, totals, and delivery addresses are immutable after creation. |
| **`BR-ORD-06`** | **Implemented (`V6`)** | **Configurable Payment Window & Expiration:** Every order sets `expiraEm = criadoEm + max(1, pedidos.prazo-pagamento-minutos)` (default `30` minutes, `expira_em > criado_em`). Unpaid orders past `expiraEm` expire to `EXPIRADO (6)` both lazily during reads/mutations and periodically via `ExpiracaoPedidosJob`. |
| **`BR-ORD-07`** | **Implemented (`V6`, `V7`) + Planned (`V14`)** | **Strict Order State Machine (`StatusPedido`):** Allowed transitions are exclusively:<br>• `AGUARDANDO_PAGAMENTO (1)` → `PAGO (2)` \| `CANCELADO (5)` \| `EXPIRADO (6)`<br>• `PAGO (2)` → `ENVIADO (3)` \| *(planned `V14`: `REEMBOLSADO (7)`)*<br>• `ENVIADO (3)` → `ENTREGUE (4)` \| *(planned `V14`: `REEMBOLSADO (7)`)*<br>• `ENTREGUE (4)` → *(planned `V14`: `REEMBOLSADO (7)`)*<br>`CANCELADO (5)`, `EXPIRADO (6)`, and `REEMBOLSADO (7)` are terminal states; illegal or backward transitions fail with `409 Conflict`. |
| **`BR-ORD-08`** | **Implemented (`V6`) + Planned (`V14`)** | **Exactly-Once Stock Restoration:** Moving an order from `AGUARDANDO_PAGAMENTO` to `CANCELADO` or `EXPIRADO` (or from `PAGO`/`ENVIADO`/`ENTREGUE` to `REEMBOLSADO` in `V14`) locks `Pedido` with `PESSIMISTIC_WRITE`, cancels any `PENDENTE` payment attempt, locks the order's `Mouse` rows in `mouse.id ASC` order, and restores `quantidadeEstoque` **exactly once**. Subsequent cancel/expire attempts never restore stock a second time. |
| **`BR-ORD-09`** | **Implemented (`V6`, `V7`)** | **Customer Cancellation Scope:** Customers (`POST /pedidos/{id}/cancelamento`) may cancel their own order **only** while `status == AGUARDANDO_PAGAMENTO` and before `expiraEm` / payment approval. Paid orders cannot be cancelled without the `V14` refund flow. |
| **`BR-ORD-10`** | **Implemented (`V7`, `V9`)** | **Administrative Shipment & Delivery Rules:** Shipping (`POST /admin/pedidos/{id}/envio`, `@RolesAllowed("admin")`) requires `status == PAGO`, matching `@Version` (`versao`), non-blank `transportadora` (synchronized with `Transportadora` in `V9`), and non-blank `codigoRastreio`, setting `enviadoEm`. Delivery (`POST /admin/pedidos/{id}/entrega`) requires `status == ENVIADO`, matching `versao`, and sets `entregueEm >= enviadoEm` (enforced by SQL `ck_pedido_rastreio`). |
| **`BR-ORD-11`** | **Implemented (`V7`)** | **Append-Only Timeline & Subject Redaction (`EventoPedido`):** Order creation and every status transition append an immutable `EventoPedido` (`status`, `ocorridoEm`, `descricao`, internal `responsavelSubject`). Customer and admin response DTOs expose `status`, `ocorridoEm`, and `descricao` while keeping `responsavelSubject` internal (never serialized publicly). |

## 7. Payments, Simulation Boundaries, Refunds & Webhooks (`BR-PAY`)

| ID | Status | Rule & Enforcement |
| :--- | :---: | :--- |
| **`BR-PAY-01`** | **Implemented (`V6`)** | **Opt-In Simulation Engine Outside Dev/Test:** `pagamentos.simulacao.habilitada` defaults to `false` outside `%dev` and `%test`. When `false`, checkout review, order creation, and simulated payment mutations are blocked (`503`/`409`), and `GET /pedidos/configuracao` exposes simulation availability and payment deadline minutes to the SPA. |
| **`BR-PAY-02`** | **Implemented (`V6`)** | **Zero Card Credential Transmission or Storage:** Card inputs (13–19 digits, holder name, non-expired `MM/AA`, 3–4 digit CVV) are validated **exclusively in browser memory** for UI demonstration. Card numbers, CVVs, expiries, and holder names must never appear in HTTP requests, `localStorage`/`sessionStorage`, database tables, or server/client logs. |
| **`BR-PAY-03`** | **Implemented (`V6`)** | **Safe Demonstration PIX Payload:** Simulated PIX generates an EMVCo BR Code and QR code from the confirmed `Pedido.total` using a non-routable `.invalid` recipient key and valid CRC16 checksum — never embedding real banking keys in demonstration mode. |
| **`BR-PAY-04`** | **Implemented (`V6`)** | **Payment Attempt Idempotency (`chaveIdempotencia`):** `POST /pedidos/{id}/pagamentos` requires a UUID `chaveIdempotencia` serialized via `pg_advisory_xact_lock`. Replaying the same key for the same order, `FormaPagamento` (`1=PIX`, `2=CARTAO`), and `ResultadoSimulacao` returns the current order state without creating a second attempt; reusing the key with altered parameters or another order fails with `409 Conflict`. |
| **`BR-PAY-05`** | **Implemented (`V6`)** | **Single Active/Approved Attempt & Retry After Refusal:** Partial unique index `uk_pagamento_ativo` (`ON pagamento(pedido_id) WHERE status IN (1, 2)`) guarantees at most one `PENDENTE (1)` or `APROVADO (2)` payment per order. If an attempt resolves to `RECUSADO (3)`, the order remains `AGUARDANDO_PAGAMENTO` with stock still reserved so the shopper may retry with a new `chaveIdempotencia` before `expiraEm`. |
| **`BR-PAY-06`** | **Implemented (`V6`, `V7`)** | **Administrative Authority Over Payment Outcomes:** Non-admin shoppers calling `POST /pedidos/{id}/pagamentos` may submit **only** `resultadoSimulado = 3 (PENDENTE)` (submitting `1=APROVAR` or `2=RECUSAR` without role `admin` returns `403 Forbidden`). Approving or refusing a pending payment (`POST /admin/pedidos/{id}/pagamentos/{pagamentoId}/decisao`) is restricted to `@RolesAllowed("admin")`. |
| **`BR-PAY-07`** | **Implemented (`V6`)** | **Payment Amount & Processing Timestamp Integrity:** `Pagamento.valor` always equals the authoritative `Pedido.total` (`> 0`). Database `CHECK` enforces `processado_em IS NULL` when `status == PENDENTE (1)` and `processado_em IS NOT NULL` for all resolved states (`APROVADO`, `RECUSADO`, `CANCELADO`, `ESTORNADO`). |
| **`BR-PAY-08`** | **Implemented (`V6`)** | **Approval vs. Expiration Race Guarantee:** Payment resolution locks `Pedido` before `Pagamento` and verifies `Instant.now()` against `pedido.expiraEm`. Any approval attempt arriving after `expiraEm` is rejected as late, expiring the order (`EXPIRADO`), cancelling the pending payment, and restoring stock once. |
| **`BR-PAY-09`** | **Planned (`V14` — Epic E6)** | **Atomic Refunds (`REEMBOLSADO` / `ESTORNADO`):** Administrative refund (`POST /admin/pedidos/{id}/estornar` on `PAGO`, `ENVIADO`, or `ENTREGUE` orders) and customer self-service refund on unshipped `PAGO` orders atomically transition `Pedido.status` to `REEMBOLSADO (7)` and the `APROVADO` `Pagamento.status` to `ESTORNADO (5)`, record `estornadoEm` and `motivoEstorno`, restore stock (and coupon usage) once, and append an `EventoPedido`. |
| **`BR-PAY-10`** | **Planned (`V15` — Epic E7)** | **Pluggable Payment Gateways & Webhook Deduplication:** External provider integrations implement `PagamentoGateway`, verify webhook cryptographic signatures over the raw request body, and deduplicate events in `evento_webhook_pagamento` (`UNIQUE(provedor, evento_externo_id)`) before applying state transitions. |
